--------------------------------------------------------------------------------
    1. SYSTEM OVERVIEW & CORE PHILOSOPHY
--------------------------------------------------------------------------------
The AI-Based Intelligent Question Paper Scrutiny Decision Support System (DSS) is a web application for autonomous engineering colleges and examination cells.

Key Objectives (implemented):
- Automate quality assurance and scrutiny of college question papers before examinations.
- Enforce institutional scrutiny rules (total marks, numbering, duration, internal choice, CO coverage, unit coverage, Bloom distribution).
- Evaluate Bloom's Taxonomy cognitive levels (K1–K6 / Remember through Create).
- Validate Course Outcome (CO) mapping and syllabus unit coverage.
- Perform unit-boundary compliance (flags questions mapped to units not selected for that exam).
- Compare uploaded questions against a SAME-SUBJECT historical question bank using TF-IDF cosine similarity (not a dedicated vector DB).
- Human-in-the-loop moderator supervision: review AI evidence, optionally correct findings, record decisions (APPROVED, MODIFICATION_REQUIRED, REJECTED), export PDF/CSV/JSON.
- Multi-subject workspace isolation: syllabus, COs, units, documents, previous papers, and exam rules are keyed by subject_id. Similarity search is filtered by subject_id.
- Seed starts with user accounts only (no hardcoded mock subjects). Curriculum is teacher/admin configured, including unit add/edit/delete, topics, PPT/document upload, and syllabus file upload with regex parsing.

What this is NOT:
- Not a fully autonomous auto-approver. Moderators make the official decision.
- Not a RAG vector database (no Chroma/Pinecone/FAISS). Gemini (when enabled) receives syllabus/CO text in the prompt. Fallback is keyword heuristics.
- Stored 64-dimension hash embeddings on previous questions are written at previous-paper upload time but the live similarity search uses sklearn TfidfVectorizer on question text, not those stored vectors.

--------------------------------------------------------------------------------
    2. SYSTEM ARCHITECTURE & TECHNICAL STACK
--------------------------------------------------------------------------------
Architecture Pattern: Decoupled REST API (FastAPI backend) + React (Vite) SPA frontend.

BACKEND (ACTIVE RUNTIME):
- Language: Python 3
- Framework: FastAPI (ASGI), Uvicorn on port 8000
- Database: MongoDB via PyMongo (`MONGODB_URI`, database name `question_paper_scrutiny` by default)
- Integer IDs: MongoDB `counters` collection (`get_next_sequence`) so frontend routes like `/papers/3` still use integers
- Validation: Pydantic v2
- Auth: JWT via `python-jose` (`jose.jwt`), bcrypt via Passlib, OAuth2 Bearer (`OAuth2PasswordBearer`)
- Document extraction: PyMuPDF (`fitz` / `pymupdf`) for PDF; `python-docx` for DOCX; UTF-8 text for TXT
- Optional PPTX text extraction in `document_service.py` via `python-pptx` (try/import; not listed in requirements.txt)
- Similarity: scikit-learn `TfidfVectorizer` + `cosine_similarity`; numpy for 64-dim hash embedding generation
- Reports: ReportLab PDF (`app/utils/pdf_export.py`); CSV/JSON via `report_service`
- AI: Google Gemini through `google.generativeai` when `AI_PROVIDER=gemini` and `GEMINI_API_KEY` is set; otherwise deterministic heuristic in `gemini_service.py`

BACKEND (PRESENT IN REPO BUT NOT THE LIVE DATA PATH):
- SQLAlchemy 2 + SQLite (`app/db/database.py`, `app/models/models.py`, `app/db/init_db.py`) — leftover ORM schema and SQLite migration helpers. FastAPI `app/main.py` lifespan connects to MongoDB only; API modules use `get_db` from `app.db.mongo`, not SQLAlchemy `SessionLocal`.
- Alembic, psycopg2-binary listed in requirements.txt but not wired as the running store.

FRONTEND:
- JavaScript (ES6+), React 18
- Vite 5, port 3000, proxies `/api` to `http://localhost:8000`
- React Router DOM v6
- Tailwind CSS; light/dark theme (`ThemeContext`, default dark, persisted in localStorage)
- lucide-react icons
- recharts charts on dashboard
- axios HTTP client (`frontend/src/services/api.js`): baseURL `/api`, 180s timeout, Bearer token from localStorage, 401 redirects to `/login`

PORT MAPPING:
- Backend: http://localhost:8000  (Swagger `/docs`, ReDoc `/redoc`, health GET `/`)
- Frontend: http://localhost:3000/

--------------------------------------------------------------------------------
    7. AI / ML (CURRENT IMPLEMENTATION)
--------------------------------------------------------------------------------
Provider switch: settings.AI_PROVIDER  (`mock` default, or `gemini`)
Model: settings.GEMINI_MODEL (config default gemini-1.5-flash; .env.example lists gemini-2.5-flash; GeminiService falls back to gemini-2.5-flash if model unset)
Library actually called: google.generativeai GenerativeModel.generate_content
Package google-genai is in requirements.txt but not imported by gemini_service.py.

When Gemini is used:
- System-style prompt in _call_gemini_scrutiny: academic scrutiny engine; do not invent marks/CO/Bloom/unit/topic; parser values take precedence; return JSON array of bloom_level, co_code, unit_number, topic_name, confidence, reasoning, grammar_status, quality_status, suggested_improvement.
- JSON is stripped of markdown fences and validated with AIQuestionAnalysis.
- Bloom from AI must match K1–K6; CO must match CO + digits.

When mock / missing key / Gemini failure:
- _semantic_heuristic_analysis (verb lists for Bloom; CO description word overlap; syllabus title/topic keywords).

NOT implemented as claimed vector RAG:
- No embedding model API (OpenAI/Gemini embeddings).
- No vector database similarity index.
- Prompt stuffing of syllabus/CO lists is the only LLM context retrieval.

Similarity:
- sklearn TF-IDF unigrams+bigrams, english stop words, cosine, threshold 0.65, top_k 3, same subject_id previous bank.

Scoring: deterministic report_service from rule statuses, grammar/quality FAIL/WARNING counts, max similarity score.

--------------------------------------------------------------------------------
    21. VIVA / INTERVIEW QUESTIONS (CURRENT PROJECT)
--------------------------------------------------------------------------------

BASIC
Q: What is this project?
A: A decision-support web app that extracts questions from uploaded papers, checks institutional rules, maps Bloom/CO/units, flags similar historical questions, and lets a moderator approve, request changes, or reject.

Q: Who are the users?
A: FACULTY, MODERATOR, and ADMIN, stored in MongoDB users with JWT login.

TECHNOLOGY
Q: What is the live database?
A: MongoDB via PyMongo. SQLAlchemy/SQLite models remain in the repo but FastAPI routes use mongo.get_db.

Q: Frontend stack?
A: React 18, Vite 5, React Router 6, Tailwind, axios, recharts, lucide-react.

ARCHITECTURE
Q: How is scrutiny executed?
A: papers.upload or analyze calls extract_and_store_questions then run_scrutiny_analysis in scrutiny_pipeline.py.

Q: How are integer IDs kept on MongoDB?
A: counters collection atomic $inc in get_next_sequence.

DATABASE
Q: How is subject isolation enforced?
A: Every curriculum and paper record has subject_id; previous-paper similarity loads previous_papers with that subject_id only.

API
Q: Difference between /api/reports/{id}/decision and /api/moderator/reviews/{id}?
A: Both record moderator outcomes. The UI uses POST /api/moderator/reviews/{paper_id}, which stores corrections and maps statuses to APPROVED / MODIFICATION_REQUIRED / REJECTED.

AI/ML
Q: Do you use a vector database?
A: No. Similarity uses sklearn TF-IDF cosine. Optional Gemini classification uses syllabus text in the prompt. Hash 64-d vectors are stored but not queried.

Q: What happens without GEMINI_API_KEY?
A: AI_PROVIDER mock or missing key uses _semantic_heuristic_analysis (verbs and keyword overlap).

SECURITY
Q: How is access controlled?
A: JWT Bearer, bcrypt passwords, require_role, faculty ownership checks on papers/history/scrutiny.

Q: Are demo passwords documented here?
A: No. They are seeded in scripts/seed_data.py and must not be treated as production secrets.

PROJECT-SPECIFIC
Q: What is unit-boundary compliance?
A: If AI/heuristic maps a question to a unit not in selected_units_json, unit_validation_status becomes UNSELECTED_UNIT and rule "Exam Unit Selection Compliance" FAILs.

Q: How is the 100-point score computed?
A: report_service.calculate_score_breakdown weights marks, numbering, Bloom, CO, units, grammar/quality, similarity, time, choice.

DIFFICULT
Q: Why can marks be null?
A: Parser and _safe_marks refuse to invent default marks; unmarked questions are counted separately in the marks rule.

Q: Why might Mongo embeddings disagree with similarity results?
A: Embeddings are hash histograms written at previous-paper upload; matching uses a fresh TF-IDF matrix on texts at scrutiny time.

Q: Is syllabus upload NLP or LLM?
A: Regex/line parser in parse_syllabus_text (Unit/Module/CO patterns), not Gemini.

--------------------------------------------------------------------------------
    22. PROJECT EXPLANATION
--------------------------------------------------------------------------------

30-SECOND:
This is an examination-cell DSS: faculty upload a question paper, the backend parses questions and scores them against syllabus, COs, Bloom levels, marks rules, and past papers, then a human moderator signs off.

1-MINUTE:
The system is a React SPA and FastAPI service. Curriculum lives per subject in MongoDB. Uploaded PDF/DOCX/TXT papers are extracted with PyMuPDF/python-docx and a deterministic parser. Analysis uses Google Gemini if configured, otherwise keyword heuristics, plus a sklearn similarity check against that subject's previous questions. A rule engine and a transparent 100-point score produce a report. Moderators approve, request modification, or reject. Reports export as PDF, CSV, and JSON.

3-MINUTE:
Engineering colleges must scrutinize question papers for marks totals, choice patterns, Bloom mix, CO coverage, and unit scope (for example internals covering only units 1–2). This project isolates each subject workspace: units, topics, COs, PPTs, syllabus files, and a historical bank. On upload, questions are stored with hierarchy (groups, subquestions, internal choice) without fake marks. Gemini (or heuristics) fills Bloom/CO/unit when not printed. The rule engine compares calculated marks (capping choice groups), CO/unit coverage percentages, unselected-unit violations, and Bloom higher-order share (>=40% target). Similarity flags repeats. Moderators see evidence, can override finding values, and the audit log records login, upload, analyze, and decisions. JWT roles keep faculty from seeing other faculty papers and from issuing official decisions.

5-MINUTE DETAILED:
Start MongoDB, seed three role accounts, run Uvicorn on 8000 and Vite on 3000. An admin creates CS301. Faculty upload an official syllabus; regex extracts COs and units into Mongo. They add topics and PPTs. They index last year's paper so TF-IDF has a bank. They upload this term's paper with selected units. extract_and_store_questions writes EXTRACTED questions; run_scrutiny_analysis sets ANALYZING, calls GeminiService.analyze_paper_questions, writes mappings, loads previous_questions for that subject_id, computes cosine matches above 0.65, runs RuleEngine.validate_paper, scores with ReportService, inserts scrutiny_reports version N, and sets PENDING_REVIEW. The scrutiny page loads /api/papers/{id} and /api/scrutiny/{id}. A moderator posts /api/moderator/reviews/{id}. Faculty read history /api/history. Exports go through ReportLab and CSV/JSON builders. Leftover SQLAlchemy models and unused React pages are not on this path. AI is assistive: parser values win over the model, and the moderator is the authority.
